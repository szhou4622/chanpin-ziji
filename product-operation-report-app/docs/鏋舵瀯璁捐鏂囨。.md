# 产品经营报告 桌面 App · 架构设计文档

> 版本：v0.1（待评审）
> 日期：2026-06-26
> 来源：由现有 Codex skill「产品经营报告」(SKILL.md / SOP.md) 演化为本地桌面软件

---

## 1. 项目背景与定位

现有的「产品经营报告」是一套 **用大模型按固定 SOP 做经营分析** 的能力：把零散的一方数据（抖店罗盘 / 巨量云图 / 视频号成交人群截图、评价、退款、自有爆款素材表）、二方竞品数据、产品基础信息和素材明细，推理成一份**能讲解、能复用、能落地拍片子**的《产品经营报告》。

它**不是数据汇总工具**，而是按 SOP 把数据转成内容经营决策：谁在买、在什么场景买、为什么被打动、卖点怎么排序、视频号打什么内容主线、下一步拍什么选题。

本项目把这套能力做成一个**本地桌面软件**：自带聊天交互、文件解析、报告渲染，背后接用户自己配置的大模型 API。

### 核心设计原则

- **SOP 即引擎**：SKILL.md / SOP.md 不丢弃，直接作为编排器每一步的系统提示词 + 成稿前校验规则。
- **源绑定（source-bound）**：不编造价格、链接、背书、活动机制；3 秒开头必须来自素材表；缺数据写「需补充」。
- **人在回路**：逐步推进，关键步骤停下来让用户确认 / 修改，而不是一次性出稿。
- **数据不出本地**：素材、中间产物、成稿都存在用户本机；只有调模型时把内容发往用户自己配置的 API。

## 4. 模块设计

### 4.1 文件接入层
- 拖拽 / 选择上传，支持 `.xlsx .xls .csv .png .jpg .jpeg .webp .gif .md .txt .pdf .docx .doc .pptx .ppt .zip`，以及**整个文件夹**（webkitdirectory）。
- 表格：XLSX 用 SheetJS 解析、CSV 直接解析，转成结构化行列 + 纯文本预览。
- 文档：PDF 抽取文本（含按页，Node20 需 Promise.withResolvers polyfill）；Word(.docx) 用 mammoth 解析；PPT(.pptx) 用 jszip 解 zip 抽每页 `<a:t>` 文本 + 演讲者备注；Markdown/txt 直接读文本。
- 图片：转 base64，作为多模态消息的 image 部分。
- 压缩包(.zip) / 文件夹：自动展开，逐个解析里面支持的文件（图片走读图、文档表格抽文本），过滤系统垃圾文件（.DS_Store、__MACOSX、~$ 临时文件等）。
- 旧格式 `.doc / .ppt`（二进制）暂不支持，提示另存为 .docx / .pptx。
- PDF/PPTX 若为扫描件或纯图片页（无文本层），提示改用截图走多模态，OCR 放二期。
- 每个上传文件登记到报告工程的 `sources/`，并打「数据归属」标签：一方 / 二方(竞品) / 素材。

### 4.2 模型客户端
- OpenAI 兼容封装（`/v1/chat/completions`），请求体支持文本 + 图片（`image_url`/base64）。
- 配置项：`baseURL`、`apiKey`、`model`、`supportsVision`(布尔)、`temperature`、超时/重试。
- 多套配置可保存切换；默认指向用户当前 GPT-5.5。
- 流式输出（SSE）回传到对话面板。
- key 用 Electron `safeStorage` 加密落盘，绝不明文写配置文件。

### 4.3 SOP 编排器（核心）
带状态的状态机，步骤对应 SKILL.md / SOP.md：

| 步 | 名称 | 输入 | 产出（结构化） | 确认点 |
|----|------|------|----------------|--------|
| 1 | 确定产品 | 用户输入/资料 | 产品基础信息卡 | ✅ 用户确认产品对象 |
| 2 | 抽取数据 | 上传的各源 | 每源 → Who/Context/Why 归一 | ✅ 缺失项提示补充 |
| 3 | 锁定竞品 | 已知竞品 / 8 类方向 | 竞品清单 + 待采集项 | ✅ |
| 4 | 卖点拆解 | 产品事实 | 12 类卖点 → 用户买点 | |
| 5 | 卖点排序 | 卖点 + 人群痛点 | 排序表(转化价值) | ✅ 审校排序 |
| 6 | 核心人群画像 | 一方/二方数据 | 四类人群表 | ✅ 审校人群 |
| 7 | 内容矩阵 | 人群×痛点×场景×卖点 | 矩阵 | |
| 8 | 视频号内容主线 | 排序×人群×场景×素材 | 主线表(人群写具体描述) | ✅ |
| 9 | 执行选题表 | 主线 | 3.1/3.2/3.99 选题表(三视角) | ✅ |
| 10 | 成稿 | 全部产出 | 12 段报告 | 校验后输出 |

- 每步：构造该步系统提示词（注入 SKILL.md 规则 + 已确认的上游产出 + 相关素材）→ 调模型 → 解析成结构化 artifact → 侧栏展示 → 等用户确认/修改 → 进入下一步。
- 支持回退到任意已完成步骤重做（下游 artifact 标记为待刷新）。

### 4.4 硬规则校验（成稿前）
- 不得出现编造的价格 / 链接 / 背书 / 活动机制；缺数据须为「需补充」。
- 3 秒开头必须能追溯到某条素材表记录。
- 主线表 / 选题表的「人群」列必须是具体人群描述，禁止只写「第一主力 / 视频号核心」等内部标签。
- 不同平台人群不强行合并，须保留平台差异并回到场景/需求/诱因。
- 校验不过 → 在侧栏列出问题项，定位到对应段落，阻止/警示导出。

### 4.5 报告渲染与导出
- 12 段模板：结论先行 / 数据来源与使用范围 / 产品基础信息 / 一方数据核心判断 / 竞品与素材打法判断 / 产品全量卖点拆解 / 卖点用户视角排序 / 核心成交人群画像与卖点场景匹配 / 视频号内容主线设计 / 内容执行方向 / 经营建议 / 本次报告限制。
- 预览：Markdown 渲染（含表格）。
- 导出：Markdown 原文件；Word(.docx) 用文档库生成（标题层级、表格、目录）。

### 4.6 设置页
- 模型配置（增删改、切换、连通性测试、是否多模态）。
- 报告工程默认保存目录。
- （二期）飞书凭证、OCR 开关。

## 5. 数据模型（报告工程）

每份报告 = 一个本地文件夹：

```
<报告工程名>/
├── project.json        元信息(产品名、创建时间、当前SOP步骤、状态)
├── sources/            上传的原始素材(截图/表格原文件)
│   └── _index.json     每个文件的归属标签(一方/二方/素材)+来源类型
├── normalized.json     第2步归一结果: [{source, who, context, why}]
├── artifacts.json      各步结构化产出(产品卡/竞品/卖点/排序/人群/矩阵/主线/选题表)
├── chat.json           对话历史
└── report.md           最终成稿(导出 Word 时由它生成)
```

- 报告工程可保存、关闭、重新打开继续。
- `artifacts.json` 用版本化结构，便于回退重做。

## 6. 技术栈与主要依赖

- 外壳：Electron + electron-builder（打 Win/Mac 安装包）
- 前端：React + TypeScript + Vite；UI 组件库（待定，倾向轻量如 shadcn/Radix 或 Ant Design）
- 状态：Zustand 或 Redux Toolkit（编排器状态较重，倾向 Zustand）
- 表格解析：SheetJS(xlsx) + papaparse(csv)
- 文档解析：pdf 文本抽取(pdfjs-dist/pdf-parse) + Word(mammoth)
- Markdown 渲染：react-markdown + remark-gfm
- Word 导出：docx 库（或复用现有 docx 生成能力）
- 模型调用：fetch + SSE（OpenAI 兼容），不绑定单一 SDK
- key 加密：Electron safeStorage

## 8. 开发阶段计划

- **阶段一 · 骨架**：Electron+React+Vite 跑起来；三栏布局；设置页能配模型并成功调通一次（含发图）。
- **阶段二 · 核心闭环**：文件上传解析 + SOP 编排器走通「确定产品 → … → 成稿」全链路；对话 + 侧栏确认。
- **阶段三 · 打磨**：硬规则校验、Markdown/Word 导出、报告工程保存/重开、错误与重试处理。
- **阶段四 · 二期**：飞书一键推送、OCR 兜底、模板自定义、批量。

---

## 9. 安全与隐私

- 所有素材与产出仅存本机；联网仅发生在调用用户自配的模型 API 时。
- API key 本地加密存储，不写日志、不上报。
- 导出文件由用户决定保存位置。

## 10. 风险与开放问题（评审时一起确认）

1. 「可配置多家」下若用户配了**不支持读图**的模型，截图无法解析——v1 先用开关提示，二期加 OCR 兜底，是否接受？
2. Word 导出对复杂表格（13 列选题表）的排版精度要求到什么程度？
3. UI 组件库选型（Ant Design 上手快、偏中后台风；shadcn/Radix 更轻更可定制）。
4. 是否需要把现有那份「酸菜王」报告作为内置样例/回归测试基准？
5. 长报告 + 多张截图可能超模型上下文，是否需要分步只带相关素材（编排器已按步裁剪，但需验证）。
